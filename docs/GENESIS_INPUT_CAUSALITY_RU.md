# Этап №12 — причинная проверка управления оригинальной QuackShot

Все испытания проведены локально в Genesis Plus GX v1.7.4 на одном
пользовательском ROM, SHA-256:
30581220f6c914709853828811fe143e283896189a64eedf1444dc908b5cac34.
Сам ROM, исходные кадры, звук и содержимое RAM в GitHub не загружались.

## Почему измерения нельзя было сразу принять за физику Дональда

На экране действительно появляется Дональд, который бежит, стреляет,
прыгает и проходит несколько эпизодов, однако **видимая анимация не
доказывает, что она вызвана нашим управлением**.

Чтобы отличить самостоятельное воспроизведение от реального управления,
запускали независимые одинаковые экземпляры исходной игры:

1. Базовый запуск: только START на кадрах 450–464.
2. Такой же запуск с *одним* дополнительным действием на установленном
   участке (RIGHT, LEFT, A, B либо START).
3. Контрольные суммы полных выходных кадров и 64 КиБ RAM сравнивали на
   совпадающих номерах кадров.
4. Дополнительно считали, сколько раз эмулятор получил активное
   состояние указанной кнопки, чтобы исключить ложное предположение,
   будто кнопка вовсе не была подана.

Новый инструмент: tools/genesis_input_causality.py.

Он запрещает публикацию исходных байтов, сравнивает повторные запуски
контрольного сценария на детерминизм, а при обнаружении несопоставимых
состояний прекращает анализ.

## Измерения с точностью до одного видеокадра

| Добавленная команда | Видеокадры | Изменилось кадров | Изменилось снимков RAM |
|---|---:|---:|---:|
| RIGHT, 1300–1369 | 1600 | **0** | 0 из 27 |
| B, 1300–1369 | 1600 | **0** | 0 из 27 |
| A, 1300–1369 | 1600 | **0** | 0 из 27 |
| LEFT, 3200–3319 | 3330 | **0** | 0 из 56 |
| START, 3200–3214 | 3330 | **128** | 2 из 56 |

Для START первый изменившийся видеокадр — **3202**.
Первый отличный снимок RAM приходится на контрольную точку **3240**,
так как RAM пока снимается с периодичностью 60 кадров.

В отдельных более длинных прогонах по 3700 кадров направления и
кнопки A/B также не влияли на сравниваемые контрольные суммы.
А START на кадрах 3200–3214 менял 8 из поздних 60-кадровых
контрольных точек. На приватных кадрах после этой команды
наблюдалось повторное появление заставки **SEGA**.

Измеренные активные вызовы контроллера подтверждают, что варианты
RIGHT/A/B/LEFT действительно поступали в frontend libretro.
Следовательно, данные не позволяют объяснить отсутствие изменений
простым пропуском пользовательского ввода на уровне нашего callback.

## Дополнительный поиск активного окна управления

Проверил **ещё 15 раздельных окон RIGHT** длительностью по 60 кадров
с началом на кадрах 300, 550, 700, 850, 1000, 1150, 1450, 1750,
2050, 2350, 2650, 2950, 3450, 3900 и 4350. Контрольная игра
каждый раз независимо запускалась с START на 450–464.

На каждом из 15 интервалов ядро получало 60 активных чтений RIGHT.
Однако **ни одна контрольная CRC32 видео с интервалом 10 кадров**
не отличалась от соответствующего независимого базового прогона.

Это расширяет подтверждённый интервал неотзывчивой по видео
автоматической последовательности, но не означает, что игра
никогда не реагирует на джойстик: поиск не охватывал все возможные
времена, состояния, комбинации и промежуточные RAM-переходы.
Планировавшийся более длинный поиск был прекращён после
15 завершённых экспериментов, а не завершён полностью.

## Выводы и ограничения

Подтверждённые факты:
- START изменяет видеопоследовательность и RAM.
- На указанных участках движения/действия не вызывают наблюдаемого
  различия в видео и RAM относительно идентичного контроля.
- Заставка SEGA после позднего START говорит о возврате к начальной
  последовательности.

Пока не подтверждено:
- Что анимированный персонаж в этих кадрах действительно управляем.
- Любой адрес RAM, хранящий координаты Дональда.
- Скорость движения, высота прыжка или длительность анимации вантуза.
- Что отсутствие различий на контрольных кадрах исключает кратковременные
  изменения между снимками RAM.

**Нельзя переносить движения персонажа из демонстрационной
последовательности в физику Switch-ремейка как эталон**.

## Воспроизводимый локальный запуск без загрузки ROM в GitHub

Нужны Linux x86-64, локальный файл Genesis Plus GX из успешного ROM-free
GitHub Actions и приватный пользовательский ROM:

    python3 tools/genesis_input_causality.py --core /private/genesis_plus_gx_libretro.so --rom "/private/QuackShot Starring Donald Duck.gen" --expected-sha256 30581220f6c914709853828811fe143e283896189a64eedf1444dc908b5cac34 --frames 3700 --base 450:465:START --variants "walk@1300:1370:RIGHT,jump@1300:1370:B,restart@3200:3215:START" --output /tmp/quackshot-input-causality.json

Для сравнения *всех* видеокадров добавьте --stride 1. При таком режиме
RAM по-прежнему снимается раз в 60 кадров; инструмент не обещает
покадровую RAM-трассу. Программа пишет только числовые контрольные
суммы и номера кадров. Пути к приватным данным не выводятся в отчет.

GitHub Actions запускает модульные тесты только на искусственных
последовательностях и никогда не открывает оригинальный ROM.

## Следующий шаг

Искать путь из заставки/демонстрации в **настоящий управляемый уровень**.
Для этого использовать короткие раздельные нажатия START/A/B на
разных экранах, сохранять локальные контрольные снимки,
проверять текущий режим по независимым признакам. Только после
обнаружения воспроизводимого влияния RIGHT/JUMP/FIRE можно применять
метод разностных RAM-снимков для поиска координат и скоростей.
