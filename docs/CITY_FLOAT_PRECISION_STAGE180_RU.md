# QuackShot Remake — Stage180: аудит точности float относительно 16.16

## Почему нужен аудит

Экспериментальный профиль CITY TEST хранит координаты и скорости как 32-битные `float`. Для приватно исследованной Mega Drive-версии наблюдаемые поля положения относятся к числовому формату 16.16, где **одна минимальная единица равна 1/65536 пикселя**. У `float` 24 значащих двоичных бита, поэтому шаг между соседними представимыми значениями зависит от величины X.

Проверка `tests/test_reference_city_precision_audit.c` фиксирует эти свойства через `nextafterf()` как **числовое ограничение инженерной модели**, а не реконструкцию оригинального кода.

| World X | Происхождение ориентира | Шаг float в единицах 16.16 |
|---:|---|---:|
| 61 | измеренная стартовая координата CITY | 0,25 |
| 142 | измеренный ориентир первого движения камеры | 1 |
| 396 | измеренный ориентир первого уступа | 2 |
| 423 | измеренный ориентир нижней поверхности | 2 |
| 498 | измеренный ориентир стены | 2 |
| 640 | авторская контрольная координата | 4 |
| 1200 | авторская контрольная координата | 8 |

Например, при X=396 прибавление *ровно одной* минимальной единицы 16.16 к `float` может округлиться обратно в X=396. Это не свойство нового алгоритма столкновений, а ограничение формата `float`. Поэтому строгую идентичность **произвольных** исходных состояний 16.16 невозможно гарантировать одной лишь заменой допуска на `nextafterf()`.

## Что уже может быть точно воспроизводимо

Важно не смешивать теоретическую точность форматов с ошибкой на реальных маршрутах. Ранее измеренная горизонтальная модель использует шаг ускорения `10240/65536 = 5/32` и предел скорости `106496/65536 = 13/8`. Эти значения находятся на более грубой двоичной сетке, чем минимальная единица 16.16.

Второй раздел теста сравнивает **720 кадров авторской последовательности** RIGHT, нейтраль, LEFT, нейтраль, RIGHT, LEFT с независимой целочисленной арифметикой 16.16 и `float`. Он запускается с X=61 и X=396, проверяя на каждом шаге точное равенство координаты и скорости. Это тест выбранной горизонтальной модели, не воспроизведение записи ROM/BK2 и не гарантированная точность всех других физических или игровых операций.

## Практический вывод

- Stage179 устраняет пропуск *представимых* положительных перекрытий менее 0,01px.
- Stage180 выявляет места, где минимальное дробное значение исходного 16.16 **вообще нельзя представить** во `float`.
- Для будущего строгого покадрового сравнения произвольных оригинальных состояний нужно рассмотреть отдельное целочисленное 16.16 состояние (с контролем переполнений) либо явно документировать допустимую ошибку.
- Простая конвертация float↔16.16 после каждого кадра без полного понимания порядка операций оригинала не делает движок эквивалентным исходной игре.

В публичный GitHub попадают только числовые ориентиры и оригинально-независимый тест. ROM, BK2, видеокадры, графика, аудио, инструкции игры и сырые RAM-дампы не добавляются. Игровой код, механика и стандартный прототип в Stage180 не изменяются.

## Запуск

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel
ctest --test-dir build -R reference_city_precision_audit --output-on-failure
./build/qs_city_precision_audit_tests
```
